# 设计说明：本地话题录制与回放组件（无 ROS 依赖）

本组件用本地发布/订阅（`bag.Bus`）模拟 ROS 话题通信，用本地目录保存录制数据，
目标是让「长时间录制」「中途崩溃」「消息定义演进」三类场景的行为完全可预期。

## 1. 存储与索引布局

一个 bag 就是一个目录：

```
<bagDir>/
  manifest.json            版本号 + topic -> schema id 列表（定义演进历史）
  schemas/<schemaID>.json  消息定义，内容定址、不可变
  data/<topicFile>.bag     该话题的追加帧文件（topic 名经百分号编码）
  data/<topicFile>.idx     打开时扫描重建的索引缓存（可随时删除，不影响正确性）
```

- `schemaID = hex(sha256(canonicalJSON(def))[:16])`：定义内容相同即同一 id，
  注册顺序不影响 id；同一 topic 每次注册内容不同的定义都会在 manifest 中追加，
  形成演进历史，写入时使用最新版本。
- `manifest.json` 与每个 schema 文件都采用「写临时文件 + rename」原子替换。
- 话题文件名做百分号编码（`/a` → `%2fa`），避免以 `/` 开头的话题名产生路径
  穿越或 `/a` 与 `a` 冲突。

### 帧格式（大端）

```
magic    4B   固定 9D 5B A2 17
u32      payloadLen（从 timestamp 到帧尾 CRC 前的字节数）
u64      timestamp（UnixNano，业务时间戳）
u64      seq（同一 topic 内单调递增的写入序号）
u16+[]B  schemaID
payload  TLV 消息体
u32      CRC32-IEEE（覆盖 magic 到 payload 末尾）
```

写入路径：`Write` 把整帧通过一次 `O_APPEND` 文件写落盘后立即 `fsync` 才返回。
因此崩溃的原子语义是：**一帧要么完整存在并通过 CRC，要么不存在**。

### 打开时的恢复扫描

读取端不依赖 `.idx`，而是从头顺序扫描数据文件：

- CRC 正确、边界连续的帧进入内存索引；
- 文件尾部不完整（长度不足、`payloadLen` 越界、CRC 错）→ 判定为崩溃留下的
  半截尾帧，计入 `RecoveryReport.TruncatedTail`，**从不返回给读取方**；
  读写模式打开时会把文件物理截断到最后一条完整帧边界，保证后续追加安全；
- 文件中间无法解析时，从下一位置搜索 magic 尝试**重同步**：
  重同步成功 → 标记该 topic `Corrupt=true`，严格读取直接返回 `ErrCorrupt`
  （`RangeFilter.Lenient` 可尽力返回坏帧之后的完整帧，同时通过
  `Snapshot.Recovery` 明确告知丢帧）；无法重同步的尾部残块按截断处理。

内存索引项为 `(timestamp, seq, schemaID, offset, length)`。查询区间时在
有序的时间戳上二分/线性过滤，再用独立只读文件句柄按 `(offset, length)`
`ReadAt` 取帧并二次 CRC 校验。

## 2. 读取的一致性：快照（Snapshot）

`Storage.Snapshot()` 深拷贝创建瞬间的索引，并为数据文件打开独立的只读句柄：

- Writer 继续追加、fsync、甚至崩溃截断（恢复发生在 Open 时，运行中不会截断），
  都不会改变已有快照内容；
- 快照永远看不到半帧（半帧不进索引），因此「边录边读」读到的内容一致且
  快照内消息数单调不减；
- 多个快照、快照与写入可并发使用（内部用 mutex 串行化 Writer 的元数据更新）。

## 3. 三类结果的区分（不混淆）

| 场景 | 判定方式 |
|---|---|
| 区间内本来没有完整消息（含未知话题） | `errors.Is(err, bag.ErrNoData)` |
| 数据损坏（坏 CRC、中间坏帧、偏移处校验失败） | `errors.Is(err, bag.ErrCorrupt)` |
| 消息定义与当前定义不兼容 | `errors.As(err, *bag.IncompatibleError)` |

## 4. 消息线格式与定义兼容规则

字段按 TLV 自描述：`typeTag(u8) + nameLen(u16) + name + value`。
**字段按名字识别而不是按位置**，数组元素同样带类型标签（名为空），
嵌套消息为 `u32 字段数 + 字段…`。

按「当前定义」回放旧数据时：

| 演进动作 | 行为 |
|---|---|
| 新增字段（含嵌套新增） | 接受；填入**固定且可解释**的类型默认值，并在 `Defaulted` 中列出字段路径 |
| 删除字段 / 改名字段 | 拒绝；`IncompatibleError` 明确指出字段「exists in recorded data but is removed/renamed」 |
| 字段类型变化（含数组元素类型） | 拒绝；原因同时给出录制类型与当前要求类型 |
| 定义完全相同 | 复用同一 schema id，无默认字段 |

固定默认值：`bool=false`、`int64=0`、`float64=0`、`string=""`、
`bytes=[]`、`array=[]`、`message` 为嵌套字段递归默认值的 map。
默认值是「零值」这一固定规则，不做任何业务猜测。

## 5. 回放（Player）的时间语义

- 回放列表在构造时一次性冻结并按 `(timestamp, topic, seq)` 排序；
  同一时间戳的多条消息间隔为 0，仍严格相邻按序发出，保证不重、不漏、不倒序。
- 首条立即发出；之后第 n 条的墙钟发出时刻：
  `wall_n = wall_0 + (t_n - t_0) / Speed`。
- **暂停/恢复**：暂停只冻结墙钟，恢复时把暂停时长补回时间锚点
  （`anchorWall += pausedFor`），消息之间的相对节奏不被压缩或拉伸。
- **跳转**：游标移动到「时间戳 ≥ t 的第一条」（二分），以该条重置时间锚点：
  跳转点之前的消息不会补播（不重），之后的消息继续按节奏发出（不漏）。
  暂停中跳转只移动游标，恢复后从新位置开始计时。
- **循环**：最后一条发出后游标归零并在当前墙钟重新锚定，不补跨轮的巨大间隔。
- 播放结束（非循环）后输出通道关闭；控制指令（暂停/恢复/跳转/停止）即使在
  等待定时器期间也即时生效。

## 6. 区间查询与截取

`RangeFilter{Topics, Start, End}` 为闭区间 `[Start, End]`，零值表示不限制
该侧；`Topics` 为空表示全部话题。`Snapshot.Clip(dst, filter, defs)` 把区间内
消息按当前定义重新编码写入新 bag，因此截取产物的定义与调用方一致；
演进不兼容会原样返回错误并中止，不产出半成品。

## 7. 验证方法

```bash
go test -v ./...          # 业务分组日志：=== [业务: ...] 用例: ... ... PASS
CGO_ENABLED=1 go test -race ./...
```

覆盖的业务与用例：

- **中断恢复**：半截尾帧可读且被截断、截断不算损坏、恢复后追加连续可读、
  seq 无重复、中间坏帧标记 Corrupt 并重同步、空区间 ErrNoData 与损坏可区分；
- **消息定义演进兼容**：新增字段默认值与路径（含嵌套）、删除/改名拒绝、
  标量类型与数组元素类型不符拒绝并给出双方类型、相同定义复用；
- **并发录制与读取**：多 goroutine 发布、持续录制中反复快照、最终无丢失无
  重复、快照单调一致；
- **同一时间戳与乱序时间戳**：乱序写入读取有序、同刻多消息稳定排序、
  闭区间边界、Clip 截取一致；
- **回放时间语义**：原速/变速墙钟耗时、暂停恢复不丢不重不漂移、
  跳转不重不漏、循环每轮完整、区间回放。

## 8. 已知边界

- `Write` 采用每条消息 fsync 的最稳策略；超长录制的吞吐可通过增加分卷
  （segment）与分组刷盘策略进一步优化，帧格式本身已天然支持按文件分卷。
- Bus 订阅者 channel 满时丢消息（模拟实时队列溢出）；录制器使用 4096 缓冲，
  消费速率应跟得上发布速率。
